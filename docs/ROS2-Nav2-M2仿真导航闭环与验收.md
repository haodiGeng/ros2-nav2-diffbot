# ROS 2 / Nav2 自主导航项目 M2 仿真导航闭环与验收

整理日期：2026-11-22。阶段验收完成日期：2026-11-21。

**M2 已完成简单静态仿真场景的导航闭环验收。**在 M1 环境基础上，使用 BCR Bot 完成仿真、运动控制、SLAM 建图、地图保存、AMCL 定位和 Nav2 自主绕障到点，并通过整套进程重启与一次 Ubuntu 完全关机开机复测。本说明用于后续启动、复盘和进入自建机器人适配阶段。

## 1. M2 的目标与完成范围

M1 确认各个基础工具能运行；M2 将这些工具连接起来，让一台参考机器人能够感知环境、生成地图，并在地图上自主到达目标。

整个流程分为两种运行模式。

- **建图模式**：仿真提供激光和里程计，SLAM Toolbox 根据这些数据逐步生成地图。需要控制机器人移动，补充不同位置的观测。
- **已知地图导航模式**：地图服务器加载保存的地图，AMCL 估计机器人在地图中的位置，Nav2 规划路线并通过速度指令驱动小车。当前统一启动入口使用这种模式，不会自动重新建图。

本阶段完成的是约 6 × 6 米、有围墙和固定箱体的简单场景。完整仓库、动态障碍和真实机器人不是本轮验收范围。

## 2. 最终采用的环境与方案

| 项目 | 当前方案 | 用途 |
|---|---|---|
| 运行环境 | VMware 中的 Ubuntu 22.04，ROS 2 Humble | 运行仿真、定位和导航节点 |
| 仿真器 | Gazebo Fortress，无图形界面运行，软件渲染 | 减轻虚拟机图形负担，产生物理运动与传感器数据 |
| 参考机器人 | BCR Bot，启用二维激光，关闭相机与双目 | 先建立能重复运行的导航基线 |
| 建图 | SLAM Toolbox | 生成并保存地图 |
| 定位 | AMCL | 计算机器人在已有地图中的位置 |
| 全局规划 | NavFn，use_astar=false | 在全局代价地图上规划路径；不是自研 A* |
| 局部控制 | Regulated Pure Pursuit，简称 RPP | 跟踪路径，并根据曲率与障碍距离调节速度 |
| 通信 | Cyclone DDS，ROS_DOMAIN_ID=23 | 统一本轮节点通信环境 |
| 仿真隔离 | IGN_PARTITION=bcr_m2 | 区分 Gazebo 通信环境 |
| 里程计 | 仿真 world 里程计 | 本轮验证导航链路，尚未评估真实轮式里程计误差 |

BCR Bot 来源为 [blackcoffeerobotics/bcr_bot](https://github.com/blackcoffeerobotics/bcr_bot)，使用 ros2 分支，固定提交 `e022fa0ce466bf8faec636454e90fbffa585a718`，许可证为 Apache-2.0。切换参考机器人改变了模型、驱动、话题及导航参数，项目仍然围绕 ROS 2、SLAM 和 Nav2 自主导航展开。

| 重启复测与归档 | 连续四目标、进程重启、Ubuntu 关机开机复测 | 确认结果不依赖临时终端状态，保留可复查证据 |

## 4. 关键接口与数据关系

| 接口 | 本项目的名称 | 作用 |
|---|---|---|
| 仿真时钟 | `/clock` | 为启用 use_sim_time 的节点提供统一时间 |
| 二维激光 | `/bcr_bot/scan` | 用于建图、定位和障碍检测 |
| 里程计 | `/bcr_bot/odom` | 提供运动估计与速度信息 |
| 底盘速度 | `/bcr_bot/cmd_vel` | 驱动仿真机器人；统一入口包含速度转发脚本 |
| 地图 | `/map` | 保存环境的占据栅格 |
| 定位结果 | `/amcl_pose` | 机器人在地图中的估计位姿 |
| 导航动作 | `/navigate_to_pose` | 接收目标并返回导航状态 |

主要坐标关系为：`map → odom → base_footprint → base_link → two_d_lidar`。AMCL 提供 map→odom，底盘运动链路提供 odom→base_footprint，机器人描述提供底盘到传感器的固定变换。导航期间不能用固定的 map→odom 代替 AMCL 定位验收。

## 5. 重要问题及最终处理

### 5.1 早期 TurtleBot 4 排查

曾出现 VMware 黑屏或图形无响应、激光全部为约 0.164 米、桥接世界名不匹配，以及差速控制器未配置或未激活等问题。逐步恢复了正常激光、运动和部分导航，但复杂场景的持续运行仍遇到困难，因此转向更容易控制变量的 BCR 简单场景。早期结果保留在原工作空间，不再作为当前启动方法。

激光话题存在，不代表它有有效数据。例如 Gazebo 中的扫描位于 default 世界，而桥接进程订阅 warehouse 世界时，ROS 端可能有发布端，却收不到扫描。排查时需要同时检查话题名称、消息内容和数据是否持续更新。

### 5.2 AMCL 无法持续取得 TF

实时激光和独立 TF 查询正常时，AMCL 仍可能因内部线程死锁无法推进。通过调用栈发现 tf2 0.25.23 的锁等待链与 [geometry2 上游问题 992](https://github.com/ros2/geometry2/issues/992) 一致；更换 DDS 没有单独解决问题。

在 `/home/geng/tf_fix_ws` 中为 geometry2 0.25.23 构建局部 tf2 修复，核心处理是在内部锁释放后执行已完成请求的回调。统一入口加载该覆盖工作空间，未覆盖系统 `/opt/ros/humble` 安装。关机开机后已确认 AMCL 实际加载修复库。该补丁仍是项目内验证用修复，完整并发与取消行为回归尚未完成。

### 5.3 地图只有一小块与定位漂移

早期 7 × 7 格的小地图不能说明正常建图，排查发现激光数据异常。恢复有效米级扫描后，地图范围明显扩大。机器人不移动也应能观测视野内的墙面或障碍；移动用于扩大覆盖，并不能修复错误的激光数据。

后续某次导航失败时，AMCL 与 world 里程计位置差约 0.95 米，把机器人估计到了障碍附近。最终针对当前 world 里程计，将 AMCL alpha1～alpha5 调为 0.005，max_beams 调为 180，激光最大距离设为 16 米，运动更新阈值设为 0.1 米和 0.1 弧度。切换到真实轮式里程计后必须重新评估这些参数。

### 5.4 绕障耗时过长与脚轮范围遗漏

原配置的膨胀半径 0.55 米小于车体半径，后调整为 0.90 米。DWB 调参后仍出现一次约 87 秒、7 次恢复的绕障，因此最终通过对照测试采用 RPP。

另外，车身外有半径 0.06 米的脚轮，轮心位于 `(±0.45,±0.27)`。覆盖脚轮所需圆半径至少约 0.5848 米，原 0.58 米略小，最终两套代价地图均采用 **0.60 米**。旧轨迹只检查车身矩形时没有重叠，但计入脚轮后出现重叠采样。控制器和车体范围均有调整，不能把全部改善只归因于更换控制器。

最终 RPP 期望线速度为 0.26 m/s、前瞻距离 0.40 米，启用碰撞检测、曲率减速和障碍距离减速。进展检测为 10 秒内移动超过 0.20 米。[RPP 对应版本官方说明](https://github.com/ros-navigation/navigation2/blob/1.1.20/nav2_regulated_pure_pursuit_controller/README.md)

## 7. 下次如何启动和验证

以下命令都在 **Ubuntu 终端**执行。先登录 Ubuntu 桌面，确保没有同一场景的旧仿真或导航实例；不能在原实例运行时重复启动。

### 终端 A：启动整套导航

```bash
bash ~/bcr_ws/validation/start_navigation.sh
```

该入口自动加载 Humble、BCR 工作空间和 TF 修复库，设置 Cyclone DDS、ROS_DOMAIN_ID=23、IGN_PARTITION=bcr_m2、软件渲染，启动仿真、单套定位和导航及速度转发。等待日志出现导航节点已激活。当前启动的是无 GUI 仿真，因此没有 Gazebo 窗口不代表没有运行。

初始位姿按本场景出生点配置。该设置用于新仿真实例从固定出生点开始，不能用于机器人已经移动后任意重置定位。

### 终端 B：基础查看或执行四目标验收

```bash
source /opt/ros/humble/setup.bash
export ROS_DOMAIN_ID=23
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp

# 可选基础查看
timeout 10s ros2 topic echo /clock --once
timeout 10s ros2 topic echo /bcr_bot/scan --once --field header \
  --qos-reliability best_effort
```

如需重复同一轮验收，应从新启动的仿真出生点开始，再在终端 B 执行：

验收脚本以 Windows `artifacts/bcr/navigation_regression.py` 的当前副本为准。执行前确保 Ubuntu `validation` 中已同步该版本；旧版本可能使用固定输出文件名，不支持下面的文件名参数。

```bash
python3 ~/bcr_ws/validation/navigation_regression.py new_regression.json
```

脚本会实际驱动机器人，连续发送 `(2.2,0) → (0,0) → (2.2,0) → (0,1.4)`，保存结果到 Ubuntu `validation/new_regression.json`。测试期间不要同时键盘遥控或从 RViz 发送其他目标。状态 4 表示该目标成功；还应一起检查恢复次数、运行日志和轨迹，而不是只看到“目标已接受”就判定完成。

### 停止与保存

先等待导航完成并确认停车，在终端 A 用 `Ctrl+C` 结束整套启动；等待退出后再关闭 Ubuntu。手工后台或 SSH 启动的实例应按对应启动进程停止，不能只关闭查看数据的终端。

普通已知地图导航不需要每次重新保存地图。只有重新建图或修改地图时，才需另存地图及相关建图数据；修改了参数或脚本时，同步备份到 Windows 项目目录。不要用旧文件覆盖当前已验收配置。

## 8. 最终验收结果

### 可选 Gazebo 三维界面

2026-11-22 增加了方向灯 `demo_sun`，解决最小场景中地面和模型过黑的问题。运行仿真后，可在另一个 Ubuntu 桌面终端执行以下命令，为现有仿真连接三维 GUI，不会启动第二套仿真：

```bash
bash ~/bcr_ws/validation/start_gazebo_gui.sh
```

GUI 适合观察场景和机器人实际运动，RViz 适合查看地图、定位和路径。首轮 GUI 演示中，机器人成功返回原点，但耗时 67.88 秒、恢复次数为 5，尚未达到无 GUI 基线的表现，不能仅凭窗口正常显示认定带 GUI 运行同样稳定。结果见 `artifacts/bcr/gazebo_gui_demo_result.json`；该差异的原因尚需排查。关闭这个独立 GUI 窗口即可停止显示，后台导航仍可运行。

### 已验收的无 GUI 基线

2026-11-21，Ubuntu 完全关机后重新开机，直接使用保存的入口启动，未重新调参、重新建图或手动发布初始定位。连续测试结果如下。

| 连续目标 | 最终状态 | 实际耗时 | 恢复次数 | 最大采样位置偏差 |
|---|---|---|---|---|
| `(2.2,0)` | 4，成功 | 17.71 秒 | 0 | 0.029 m |
| `(0,0)` | 4，成功 | 17.96 秒 | 0 | 0.050 m |
| `(2.2,0)` | 4，成功 | 16.41 秒 | 0 | 0.048 m |
| `(0,1.4)` | 4，成功 | 23.86 秒 | 0 | 0.122 m |

四个目标之间没有重置 AMCL。车身矩形及四脚轮投影与测试箱的离散几何重叠采样均为 0；该检查不覆盖所有附件，不能替代接触传感器或连续碰撞检测。位置偏差为 AMCL 与邻近时间戳 world 里程计之差，不能作为真实轮式里程计条件下的定位精度。

原始数据可查阅 [冷启动轨迹](../artifacts/bcr/cold_reboot_rpp_regression.json)、[几何复核摘要](../artifacts/bcr/cold_reboot_rpp_regression_summary.json)、[运行日志](../artifacts/bcr/cold_reboot_rpp_navigation.log) 和 [环境记录](../artifacts/bcr/cold_reboot_rpp_environment.json)。运行配置与 Windows 副本指纹一致，重启后修复库加载正常。

## 9. M2 完成后的边界与下一阶段

目前可以把 BCR 简单场景作为可复现基线，进入自建机器人模型与导航配置适配。适配时逐项核对机器人尺寸及所有外伸碰撞体、轮距与轮径、雷达安装位姿、话题名称、TF、控制接口及导航参数，再复用本阶段的验证方法。

以下事项仍需后续单独完成：复杂仓库与动态障碍验证、轮式里程计及真实误差评测、TF 本地补丁完整回归、自研 A* 的实现与对照评测。这些不在当前 M2 已验收结论内。
